## D-004 2026-09-21 GPU memory is not visible to memcg on GB10 (R03)
Measured on peer (`gpu_memcg_probe`): a 3 GiB CUDA allocation inside a lease with MemoryMax=2 GiB succeeded; lease memory.current barely changed. `torch.cuda.mem_get_info` reported only ~6 GiB "free" (MemFree, excluding reclaimable page cache) of 119.6 GiB. Decision: leases carry a declared `gpu_memory_bytes` that is added to the aggregate memory sum; every GPU workload calls `rrp.ops.gpu.apply_cap()` (torch per-process memory fraction; tested: allocation beyond cap raises OOM in-process); system MemAvailable watchdog is the backstop. Host GPU remains disabled: cgroups cannot bound it.

## D-010 2026-09-21 thermal guard based on throttling evidence
The initial 95 C CPU shed threshold repeatedly killed healthy peer jobs (evidence: ops/watchdog/peer.jsonl, leases 1790033520_d98918, 1790038081_a0568e). ## D-013 2026-09-21 dual-arm runtime semantics needed by the supplied support_insert graph
Prior: the task runtime evaluated only `event_succeeded` among validated_receipt predicates; everything else was UNKNOWN. Evidence: in DualSession runs, `align` (precondition anchor_valid) and `insert` (precondition receipt_valid) stayed in `precondition_unknown` indefinitely; after a failed `align` attempt, `insert` kept requiring `align#0.aligned`, because rebinding was triggered only by role-binding consumers; unchanged maintained anchors were re-issued as a new receipt version on every tick (covariance was popped before storage but not before the comparison). Decision: `anchor_valid`/`receipt_valid`/`frame_valid` evaluate the latest bound receipt (missing = known-invalid); guard-condition and `frame_binding` consumers trigger recovery rebinding, and the rebind edit moves `frame_binding`; the maintained-output comparison uses the stored form. All are backwards compatible (the existing runtime/native/intervention tests pass). Effect on claims: before this change the supplied support_insert graph could not complete under any controller.

## D-085 2026-09-26 ROOT CAUSE: the semantic recipe's unbounded probe NLL starves system 0 (shared gradient clipping); sem-vs-nosem comparisons D-059/D-079/D-082/D-084 are CONFOUNDED
t1_diag (research/tracks/legged_vlm.md "T1 DIAGNOSIS", main 16db5f1). In Stage A the semantic probe loss is a Gaussian NLL whose log-variance may shrink to −8, so the loss keeps decreasing (−13 at the end) and its gradient dominates. The whole E+R+P gradient is clipped to norm 1. The sem gradient norm is 390–580 (median; nosem 0.4–1.1), so every sem update is scaled by ~0.002–0.004 (nosem 0.70–0.92). This holds in all 4 t1 seeds and also on go2/hexapod6. System 0 gets gradient only from the realization loss, so the sem system 0 trains at an effective learning rate ~250× lower (undertrained); the sem posterior σ also shrinks 10× and the packet's effective dimensionality halves. Causal tests (t1 seed 0): the sem system 0 falls even with privileged teacher-encoded packets (10/30 vs nosem 25/30), so the generator is not the cause; retraining only the sem system 0 gives a dose-response 3 → 15 → 24/30. The one-line recipe fix (bounded semantic NLL: log-variance floor −4 instead of −8; a no-op for nosem) gives sem R2 29/30 vs nosem 28/30, with probes as good as before (the per-leg contact probe becomes much better: swing accuracy 0.67 vs 0.19). Replication on seeds 1 and 3 is in progress.
Consequences: (1) D-084's "semantic supervision hurts on t1" is an artefact of this defect, not a property of semantic supervision. Every sem-vs-nosem comparison so far (D-059, D-069/071, D-076, D-079, D-082, D-084) compared a handicapped sem system 0 against a normally trained nosem one. (2) The arm sem bundle (ladder_latent_sem_b1fix_anchor) was trained with the same recipe. The arm_nosem counterpart (running) must therefore be compared against a FIXED-recipe arm sem route, not only against the frozen one. (3) The corrected claim: semantic supervision's effect is UNKNOWN pending fixed-recipe comparisons. It is not shown to help, and not shown to hurt.
